## 3. 版本与发布链路事实 [已验证]

### 3.1 版本失序（当前最优先的治理项）

| 位置                                              | 值                                                            |
| ------------------------------------------------- | ------------------------------------------------------------- |
| Git tag                                           | `v0.1.7`（指向 HEAD `8d04fc5`）                               |
| `package.json` / `Cargo.toml` / `tauri.conf.json` | 均为 `0.1.6`                                                  |
| Home 页面 UI 显示                                 | 审计时硬编码 `0.1.0`；R0-1 已改为读 `__APP_VERSION__` → 0.1.6 |
| 业务操作手册                                      | `0.1.1`                                                       |

**结论：tag `v0.1.7` 打在版本文件仍为 0.1.6 的提交上。任何"当前版本是多少"的回答都取决于问哪里。** 修复方向：引入单一版本源（见《重构路线图》R0）。

### 3.2 发布链路（两套并存）

| 链路                                                   | 触发                 | 构建目标                                                 | 产物去向                                        |
| ------------------------------------------------------ | -------------------- | -------------------------------------------------------- | ----------------------------------------------- |
| GitHub Actions `.github/workflows/release.yml`         | push `v*` tag / 手动 | Linux（deb/rpm/AppImage）+ Windows（msi/nsis），带签名   | GitHub Release + `latest.json` updater manifest |
| GitHub Actions `build-linux.yml` / `build-windows.yml` | 手动 dispatch        | 同上，用 `tauri.no-updater.conf.json`（关 updater 产物） | artifact                                        |
| Gitee `.gitee/workflows/release.yml`                   | push `v*` tag        | Linux（deb，含测试）+ Windows（nsis）                    | Gitee Release（`upload-gitee-assets.sh`）       |
| 本地 `scripts/release-all.sh`                          | 手动                 | 不构建，只 bump + tag + push 双远端                      | 依赖 CI 构建                                    |

### 3.3 发布链路风险 [静态确认]

1. **仓库布局不匹配**：`release-all.sh` 中 `REPO_DIR="$ROOT_DIR/.."` 假设项目是父仓库的子目录（与 Gitee workflow 的 `working-directory: ffmpeg_desktop` 一致）。但本机 `.git` 在项目根，remote 指向 `github.com/caoyuee/ffmpeg_desktop`。**在当前布局下直接运行该脚本，git 命令会作用于错误目录。**
2. **macOS 无 CI 构建**：`tauri.macos.conf.json` 定义了 dmg 目标，但所有 workflow 均无 macOS job。updater manifest 也只覆盖 `linux-x86_64` 和 `windows-x86_64`。
3. **updater endpoint 单点**：指向 `https://github.com/caoyuee/ffmpeg_desktop/releases/latest/download/latest.json`，对以 Gitee 为主分发渠道的用户（国内）不可达。
4. **Gitee workflow 未跑前端测试的 Windows job**：Windows 发布产物只构建不校验。

## 5. 架构级系统性问题（跨文件，需整体方案）

### 5.1 双 FFmpeg 执行路径 [静态确认]

| 维度       | legacy（`utility/_executor.rs`）                             | 新路径（`modules/task_manager.rs`）                                                     |
| ---------- | ------------------------------------------------------------ | --------------------------------------------------------------------------------------- |
| 命令解析   | 自定义双引号 parser                                          | `shell_words::split`                                                                    |
| 事件名     | `progress` / `finish` / `error`（无前缀，全局广播无任务 id） | `ffmpeg-progress` 等带前缀                                                              |
| 多任务     | 否（GLOBAL_PID 单进程）                                      | 是（HashMap）                                                                           |
| 暂停/恢复  | 否                                                           | 是（Unix SIGSTOP/SIGCONT；**Windows NtSuspend/NtResume 已实现**——旧文档称未实现是错的） |
| 前端调用方 | `useFFmpegCommand`、**QualityAssess 页面直接 invoke**        | `taskStore`                                                                             |

风险：legacy 事件无任务标识，多个监听者互相串扰；两套命令构建器（`commandBuilder.ts` vs `ffmpegCommandBuilder.ts`）随时间漂移。

### 5.2 状态管理分裂（六套并存）[静态确认]

`taskStore`（内存）、`presetStore`（Rust 文件持久化）、`settingStore`（localStorage: theme/language）、`appSettings`（localStorage: 16 字段大杂烩）、`ffmpegSettingsStore`（localStorage: 又一套 FFmpeg 配置）、`fileListStore` vs `useFileList`（两套文件列表模型）。`presetDir` 失效（P1-1）正是分裂的直接后果。

> **R2.3 已收敛（2026-11-07）**：本小节保留审计快照描述。当前设置只有 `config/settings.ts`（唯一纯函数层）与 `store/settingsStore.ts`（唯一响应式 store），持久化键只有一个 `ffmpegDesktop.settings`；文件列表只有 `store/fileListStore.ts` 的 `FileItem[]`。详见《架构与数据流》§4 与 `config/stateUnification.test.ts`。

### 5.3 PresetData 双实现手工同步 [静态确认]

TS `src/types/preset.ts`（~435 行）与 Rust `preset_manager.rs`（~525 行）手工镜像。**当前字段已基本对齐**（旧文档称 Rust 缺字段已过时），但：`createdAt/updatedAt` TS 侧为 `Date`、Rust 侧为 String；预设 JSON 无 schema version，未来无迁移能力。

> **R2.4 已收敛（2026-11-07）**：本小节保留审计快照描述。当前 Rust `preset_manager.rs` 不再定义任何预设结构体（只透传 `serde_json::Value`），前端 `types/preset.ts` 是唯一 schema（带 `schemaVersion: 1`），`config/presetSchema.ts` 负责校验 / 迁移 / 深拷贝，`createdAt/updatedAt` 统一为 ISO 字符串。详见《架构与数据流》§4 / §6 与 `config/presetSingleSource.test.ts`。

### 5.4 文档体系失治 [已验证]

已归档 4 份过期文档（`archive/`）。旧 `CLAUDE.md` 至少 6 处与代码不符（播放通知嵌套、Windows 暂停、PresetData 完整度、identifier、窗口尺寸、CSP）；README 的 pnpm 版本要求（>=8.x，实际 >=10.27）、测试覆盖率声明均不实。
