| 平台             | CI 构建                                      | 更新器支持                 | 分发渠道       | 状态         |
| ---------------- | -------------------------------------------- | -------------------------- | -------------- | ------------ |

### 3.1 发布链路风险与决策项

1. **仓库布局二义性**：`release-all.sh` 的 `REPO_DIR="$ROOT_DIR/.."` 假设"项目是父仓库子目录"（Gitee 布局）；本仓库实际 `.git` 在项目根（GitHub 布局）。**决策项：统一为 GitHub 布局后修正脚本；或维持双布局但脚本自动探测 `.git` 位置。** 在修正前，不要直接运行 `release-all.sh`。
2. **版本失序**：tag `v0.1.7` 指向版本文件为 0.1.6 的提交。发布前必须核对三处版本 + Home UI + tag 五点一致（R0-1）。
3. **updater 单点依赖 GitHub**：以 Gitee 为主渠道的用户无法获得自动更新。决策项：manifest 双托管（Gitee Pages/附件 + 跨域 endpoint 备选）或文档明示"Gitee 用户手动更新"。
4. **签名密钥**：`TAURI_SIGNING_PRIVATE_KEY`（完整私钥内容，非路径）+ 可选 password，仅存 GitHub Secrets。Gitee 侧构建未配置签名（其产物不含 .sig，天然不兼容 updater）——需在文档与 Release 说明中写明。
5. **Gitee workflow 的 `working-directory: ffmpeg_desktop`** 与本仓库结构不匹配（本仓库根即项目根），该 workflow 在当前结构下会失败——归档或修正前视为不可用。

### 3.2 标准发布流程（修正后）

```
1. 确认 R0 版本一致（package.json / Cargo.toml / tauri.conf.json / Home / 无孤儿 tag）
2. 本地：bash scripts/preflight.sh 全绿（含 coverage）
3. RELEASE_DRY_RUN=1 pnpm release:patch   # 演练：创建 commit+tag 后自动回滚
4. pnpm release:patch                     # 正式：bump→commit→tag→push 双远端
5. GitHub Actions release.yml 自动：构建（签名）→ 生成 latest.json → 发布 GitHub Release
6. Gitee 侧按 §3.1-5 的决策执行
7. 发布后人工验收：安装包可装、updater 可从上一版本升级（至少 Windows 或 Linux 之一实测）
```

## 4. 测试报告规范

`test-reports/TEST_REPORT.md` 当前内容过期且自相矛盾（覆盖率 N/A 却写"达标"）。规范：

- 每次发布/里程碑生成新报告，**只写实测数字**，标注运行环境与日期。
- 结构：类型检查 / 单测数字与覆盖率 / Rust 测试及运行环境 / E2E 范围声明 / 已知未验证项。
- 未验证项不允许省略——"未验证"本身就是必须记录的事实。

## 5. 质量文化约定（接力开发必读）

1. **禁止删测试或降阈值来"变绿"**；测试失败先怀疑实现。
2. **禁止把 [推断] 写成事实**进任何文档或 commit message。
3. 设置项新增时必须同时给出生效链路证明（吸取 `presetDir` 五项失效教训）。
4. 修 bug 时先写失败测试（红），再修（绿）——`.agents/skills/` 中 TDD 流程已定义，执行它。
5. 每个 PR 描述里回答：改了什么行为？怎么验证的？哪些没验证？
